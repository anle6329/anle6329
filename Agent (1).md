## 1. Project overview

Build a local, voice-first Windows assistant in Python.

Target pipeline:

1.  Microphone audio capture.
2.  Speech-to-text using Faster-Whisper.
3.  Local LLM using Qwen through Ollama.
4.  Distinguish normal conversation from commands.
5.  Select tools from a Python-enforced allowlist.
6.  Validate tool names, arguments, and permissions in Python.
7.  Execute approved actions.
8.  Respond using Piper TTS and audio playback.

**Security rule:** Never execute arbitrary Python, PowerShell, or CMD
code generated by the LLM.

### Speech-to-text --- considered working

Uses Faster-Whisper. The baseline is:

``` python
from faster_whisper import WhisperModel

def load_model(model_size="small", device="cpu", compute_type="int8"):
    return WhisperModel(model_size, device=device, compute_type=compute_type)

def transcribe_audio(model, audio_path):
    segments, info = model.transcribe(audio_path, beam_size=5)
    transcription = ""
    for segment in segments:
        transcription += segment.text + " "
    return transcription.strip()
```

The user considered transcription functional and moved on. Revisit only
if a bug appears.

### Command system --- baseline exists; planned redesign

Current concepts: - `tools`: tool name → Python function. -
`command_types`: intent → keyword set (legacy keyword-routing

The registry supports: - `register_tool(tool_name, tool_function)` -

The keyword router is only a temporary baseline. Limitations include

## 6. Agreed Qwen / tool architecture

The user wants Qwen to understand natural-language commands, extract
arguments, choose tools, and determine action order. However, **all
executable tools must be in a Python-enforced allowlist**.

``` text
Microphone
   |
Speech-to-Text
   |
Transcript
   |
Qwen / Ollama
   |
Structured output (JSON)
   |
Python parser + validation
   |
Allowlisted Tool Registry
   |
Argument / permission checks
   |
Execute approved tool
   |
Return result to assistant
   |
Text-to-Speech
```

Qwen may decide: - Whether the request is conversation or a command. -
Which registered tool best matches the request. - Which arguments to
supply. - The order of multiple sequential actions.

Python must enforce: - Tool name exists in the allowlist. - Argument
schema and values are valid. - Filesystem paths are permitted. - User
permission and confirmation requirements are satisfied. - The tool's
result is checked before claiming success.

Never trust model-produced JSON without parsing and validating it. Never
execute arbitrary code or shell commands generated by Qwen.

Example conceptual output:

``` json
{
  "type": "command",
  "actions": [
    {
      "tool": "open_application",
      "arguments": {
        "application_name": "Chrome"
      }
    }
  ]
}
```

For a normal question, Qwen should return a conversation response
instead. Define one consistent schema and validate it in Python.

The user wants multiple sequential commands, e.g.: "Open Chrome, then
open Spotify, and finally close Notepad."

Preserve action order. Conditional workflows are not currently required.

### Suggested module responsibilities

-   `LLM/prompts.py`: system and command-interpreter prompts.
-   `LLM/ollama_client.py`: communicate with Ollama.
-   `command/command_parser.py` (or another agreed name): parse and
    validate structured output.
-   `command/tool_registry.py`: allowlisted tools.
-   `command/command_router.py`: route validated actions to registered
    functions.
-   `action_tools/`: safe implementations.

Inspect the current repository before creating or renaming modules;
avoid duplicate responsibilities.
